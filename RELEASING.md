# Releasing

Pad starts at 1.0.0. Subsequent releases increment the patch version unless a format or installation change has been agreed. `project.yml` owns product identity, icons, version, and build configuration. Regenerate and commit the Xcode project, shared scheme, generated plist, and entitlements whenever it changes.

## Verification

Use a dedicated development Mac running macOS 27 and Xcode 27 for builds and interactive checks. Never replace or quit an installed app to test a development build. `scripts/build_and_run.sh` builds the isolated Debug product and refuses to replace it while running; `--build-only` skips opening it.

Pull requests use GitHub-hosted `xcode-27` runners, never persistent personal runners. GitHub's [image announcement](https://github.com/actions/runner-images/issues/14404) confirms its macOS 27 base. CI checks generated-project consistency, Debug tests, and a Release build. Window suites use `PAD_WINDOW_TESTS=1`; with xcodebuild, pass `TEST_RUNNER_PAD_WINDOW_TESTS=1`. Leave it unset on an occupied desktop. CI runs `FilenameInputTests` and `PanelTests` in separate, sequential xcodebuild invocations, excluding them from the main run: Swift Testing can otherwise interleave separate serialized suites that compete for the key window. Use the same suite filters for remote interactive verification.

The shared `Pad UI Tests` scheme exercises real keyboard and window interactions in an isolated desktop session. It uses launch-argument preferences to discard disposable scratch text and retains screenshots in the test result. Run it separately from all other GUI tests; it requires macOS UI testing permission. An in-process panel test does not establish that macOS accepted a foreground activation request.

## First internal TestFlight build

1. Merge a reviewed PR after CI passes. Set the version and initial build number in `project.yml`, regenerate, and commit. Verify the actual files, keyboard shortcuts, focus restoration, settings, sharing, external edits, and development/release isolation on the dedicated Mac.
2. Register the distribution bundle identifier from `project.yml` in the developer account. Create a macOS App Store Connect record with the same identifier, name, primary language, and a stable SKU. Complete required compliance and beta metadata and create an internal testing group.
3. Supply `APPLE_DEVELOPMENT_TEAM` through the existing credential manager and run `scripts/render-local-signing.sh`. It writes ignored `Config/Local.xcconfig`; never hand-edit or commit it. Regenerate the project. If the dedicated machine needs signing identities, inject the `PAD_DEVELOPMENT_PRIVATE_KEY`, `PAD_APPLICATION_PRIVATE_KEY`, `PAD_INSTALLER_PRIVATE_KEY`, matching base64 DER `PAD_*_CERTIFICATE` values and `PAD_KEYCHAIN_PASSWORD` from the credential manager, then run `python3 scripts/render-signing-identities.py`. This renders an ignored private keychain and preserves existing keychain search entries.
4. For a command-line archive, install the distribution application certificate, installer certificate, and matching App Store provisioning profile. Through the existing credential manager, provide `APPLE_DEVELOPMENT_TEAM`, `APPLE_PROVISIONING_PROFILE`, and optional certificate selectors `APPLE_DISTRIBUTION_IDENTITY` and `APPLE_INSTALLER_IDENTITY`; run `scripts/archive-testflight.sh BUILD_NUMBER` with an unused number. The defaults are Apple Distribution and 3rd Party Mac Developer Installer; select the exact installed application certificate type when different. The script renders app-only manual provisioning, supplies the team/certificate globally for package resource bundles, archives, and exports a package locally. For an isolated signing keychain, set `PAD_SIGNING_KEYCHAIN` and inject `PAD_KEYCHAIN_PASSWORD`; the script also discovers an existing `_local/signing.keychain-db`. It unlocks that keychain within the archive process and explicitly selects it for code signing, without printing the password or unlock diagnostics. The keychain must already be in the user search list so export can find its certificates. Without a task keychain, the normal login keychain is used. It never uploads. Use Xcode Organizer or the API-key upload path below to validate and upload through the intended account. Never commit signing identities, profiles, export credentials, or account-specific export options. Archive/export logs and options stay in ignored, private build output; inspect failures without publishing these files. To return to normal development signing, rerun `scripts/render-local-signing.sh` without `--distribution`.
5. Wait for App Store Connect processing, resolve any compliance questions, and add the processed build to the internal group. Install it using TestFlight on the dedicated Mac and repeat the release smoke check. Record the build, processing status, group assignment, and installation evidence privately.

An uploaded archive is not completion. The build must be installable by the internal tester. App Store publication and external beta review are separate milestones.

## API-key upload from the dedicated Mac

Inject the existing App Store Connect team API key as `ASC_KEY_ID`, `ASC_ISSUER_ID`, and PEM `ASC_PRIVATE_KEY` through its credential-manager mapping. Do not create a new Apple key or copy the local CLI keychain as a substitute for the canonical source. Then run:

```sh
python3 scripts/upload-testflight.py build/TestFlight-N/Export/Pad.pkg --wait
```

Use the actual exported package filename. This command uploads immediately, so run it only after the final commit, verification, and archive are complete. It uses Xcode 27's bundled `altool`; no separate uploader installation is needed. The script renders the key into a private temporary directory under `_local`, removes it on normal completion or Python exception, and keeps tool output in a unique private log. It never prints the key or authentication token, and strips injected `PAD_`, `ASC_`, `APPLE_`, and `INFISICAL_` variables from the uploader subprocess. If the command fails or disconnects, inspect App Store Connect and the delivery log before retrying; an ambiguous response does not mean the upload failed.

The upload derives app identity and version from the signed package. After processing, confirm the intended app, version, build number, internal group, invitation, and TestFlight installation separately. API-key source mapping and account-specific IDs belong in private operations notes, not this repository.

## Xcode Cloud owner checklist

1. Open the committed project in Xcode 27 on the dedicated Mac. In the Report navigator choose **Cloud → Get Started**. Select the distribution Pad product and the shared **Pad** scheme, then grant Xcode Cloud access to this GitHub repository and connect the existing App Store Connect record. Initial enablement must happen in Xcode; subsequent workflow edits can use App Store Connect. Start with a Release build-only onboarding run so it cannot upload a duplicate build number. [Apple onboarding guide](https://developer.apple.com/documentation/xcode/configuring-your-first-xcode-cloud-workflow)
2. In App Store Connect, open Pad → **TestFlight**, create an internal testing group if it does not yet exist, and add the intended internal tester. A group must exist before it can be selected as a Cloud distribution post-action. Do not assume repository or app creation also created this group. [Apple TestFlight workflow guide](https://developer.apple.com/documentation/xcode/distributing-your-xcode-cloud-builds-through-testflight)
3. Open Pad → **Xcode Cloud → Settings → Build Number → Edit** beside **Next Build Number**. Set it above the highest manually uploaded or already allocated release build. For example, if build 2 is the highest manual build, use 3 or higher. Do this before the first distribution run; the number must keep increasing across macOS app versions. [Apple build-number guide](https://developer.apple.com/documentation/xcode/setting-the-next-build-number-for-xcode-cloud-builds)
4. Edit the release workflow in **Xcode Cloud → Manage Workflows**. Set its environment to **Xcode 27 and macOS 27**. Replace the default branch-change start condition with **Tag Changes**, matching tags that **begin with `v`**; use `v*` only if the interface asks for a glob pattern. Remove branch, pull-request, and scheduled triggers from this distribution workflow. The repository hook rejects tags that are not exactly `vMAJOR.MINOR.PATCH` or do not match the project version. [Apple workflow reference](https://developer.apple.com/documentation/xcode/xcode-cloud-workflow-reference)
5. Add a **macOS Archive** action using the shared **Pad** scheme and its **Release** archive configuration. Choose **TestFlight and App Store** distribution, retaining eligibility for later App Store review without submitting it. Add an **Internal TestFlight Testing** post-action and select the group from step 2. Do not select an external-testing group or configure an App Store submission. [Apple distribution workflow guide](https://developer.apple.com/documentation/xcode/creating-a-workflow-that-builds-your-app-for-distribution)
6. Save the workflow. On a reviewed, green commit, validate the release tag with `scripts/validate-release.sh vX.Y.Z`, then push that tag. Confirm the Cloud archive succeeds, App Store Connect finishes processing, the internal group receives the build, and TestFlight installation works. Record the build number and installation evidence privately. A pushed tag or uploaded archive is not a delivered build.

`ci_scripts/ci_post_clone.sh` uses Cloud's `CI_BUILD_NUMBER` with `agvtool`. Its ignored `Config/Cloud.xcconfig` explicitly enables automatic signing, sets the team from `CI_TEAM_ID`, and clears the app-only manual provisioning profile. The app's Release `CODE_SIGN_STYLE` references `PAD_DISTRIBUTION_SIGNING_STYLE`, which the hook also sets to Automatic. No private local keychain, certificate export, provisioning profile, or credential-manager environment is needed in Cloud. Apple documents these supplied variables in its [environment reference](https://developer.apple.com/documentation/xcode/environment-variable-reference).

The committed project and shared scheme require no XcodeGen installation in Cloud. Source configuration is prepared; only a successful Cloud archive and distribution run verifies that the account and workflow signing work end to end.

For later releases, update the patch version, regenerate and commit the project, merge a green PR, and push the matching version tag. Cloud owns the distribution counter after handoff; never reset it or reuse a manual build number.

Do not configure Sparkle, notarized direct downloads, a CLI, or a second update pipeline for the initial release.
